## Goal

multi-tenant isolation introduced in the previous stage.

The API now supports:

- retrieving a single Node;

# 1. Nodes CRUD

Implemented endpoints:

    POST   /nodes
    GET    /nodes
    GET    /nodes/{node_id}
    PATCH  /nodes/{node_id}
    DELETE /nodes/{node_id}

## Create Node

The client provides Node data such as:

- `node_type_id`
- `display_name`
- `description`
- `properties`

The client does not provide:

- `id`
- `user_id`
- `created_at`
- `updated_at`

`id` is generated by PostgreSQL.

`user_id` is obtained from the current authenticated user dependency.

## Read Nodes

`GET /nodes` returns only Nodes belonging to the current user.

`GET /nodes/{node_id}` also includes `user_id` in the query, so another user's
Node is treated as nonexistent.

Result:

    own Node        -> 200
    nonexistent Node -> 404
    another user's Node -> 404

Returning 404 instead of exposing ownership information is intentional.

## Update Node

Nodes support partial updates through PATCH.

Only fields supplied by the client are modified.

Fields omitted from the request retain their existing values.

`updated_at` is updated when the Node is modified.

## Delete Node

A Node can be deleted only when it has no connected Edges.

If the Node participates in an Edge either as source or target:

    DELETE /nodes/{node_id}
    -> 409 Conflict

Response:

    {
      "detail": "Node has connected edges. Delete the edges first."
    }

The user must explicitly delete the relevant Edges before deleting the Node.

# 2. Edges CRUD

Implemented endpoints:

    POST   /edges
    GET    /edges
    GET    /edges/{edge_id}
    PATCH  /edges/{edge_id}
    DELETE /edges/{edge_id}

## Create Edge

The client provides:

- `source_node_id`
- `target_node_id`
- `edge_type_id`
- `description`
- `properties`

The backend automatically assigns `user_id`.

Before creating an Edge, the API verifies that both source and target Nodes
belong to the current user.

An Edge cannot connect Nodes owned by different users.

## Read Edges

`GET /edges` returns only Edges owned by the current user.

`GET /edges/{edge_id}` applies the same ownership restriction.

Result:

    own Edge          -> 200
    nonexistent Edge  -> 404
    another user's Edge -> 404

## Update Edge

Edges support partial updates through PATCH.

The following fields can be changed:

- `source_node_id`
- `target_node_id`
- `edge_type_id`
- `description`
- `properties`

When source or target is changed, ownership is validated again.

It is therefore impossible to use PATCH to move an Edge onto another user's
Node.

`updated_at` is updated when the Edge is modified.

## Delete Edge

Edges can be explicitly deleted:

    DELETE /edges/{edge_id}
    -> 204 No Content

Deleting an Edge does not delete either Node.

# 3. Graph Rules

The following graph semantics were established during Stage 3.

## Self-loops

Allowed.

Example:

    Node 10 -> Node 10

There is currently no business requirement to prohibit self-loops, so the data
model does not impose an unnecessary restriction.

## Cycles

Allowed.

Example:

    Node 10 -> Node 11
    Node 11 -> Node 10

Cycles are valid graph structures.

## Duplicate Edges

Allowed.

Multiple Edges may exist between the same source and target Nodes.

Example:

    Node 10 -> Node 11
    Node 10 -> Node 11

No uniqueness constraint is imposed on source/target/type combinations.

This leaves room for different semantic relationships and future graph
features.

## Node deletion

Cascade deletion of Edges was explicitly rejected.

Final rule:

    Node without Edges -> deletion allowed
    Node with Edges    -> deletion rejected

The user must explicitly remove graph relationships before deleting the Node.

This avoids implicit or unexpectedly destructive graph modifications.

# 4. Database Protection

Multi-tenant isolation is enforced not only by the API but also by PostgreSQL.

Edges use composite foreign keys:

    (user_id, source_node_id)
        -> nodes(user_id, id)

    (user_id, target_node_id)
        -> nodes(user_id, id)

This prevents an Edge from referencing a Node belonging to another user even if
application-level validation is bypassed.

## Node deletion protection

The Edge-to-Node foreign keys use:

    ON DELETE RESTRICT

The relevant constraints are:

    fk_edges_source_node_owner
    fk_edges_target_node_owner

This means PostgreSQL itself rejects deletion of a Node that still has connected
Edges.

Both API and database therefore enforce the same rule.

# 5. Migration

Stage 3 added the migration:

Its purpose is to replace:

    ON DELETE CASCADE

with:

    ON DELETE RESTRICT

for the two composite Edge-to-Node ownership foreign keys.

The downgrade operation restores the previous CASCADE behavior.

# 6. Type Validation

Node creation/update validates `node_type_id`.

If the referenced NodeType does not exist:

    422 Unprocessable Content

Example:

    {
      "detail": "Node type not found"
    }

Edge creation/update validates `edge_type_id`.

If the referenced EdgeType does not exist:

    422 Unprocessable Content

Example:

    {
      "detail": "Edge type not found"
    }

Source and target Nodes are also validated before Edge creation or reassignment.

---

# 7. API Error Semantics

The following behavior is currently used:

    200 OK
        successful GET or PATCH

    201 Created
        successful POST

    204 No Content
        successful DELETE

    404 Not Found
        resource does not exist or belongs to another user

    409 Conflict
        attempt to delete a Node that still has connected Edges

    422 Unprocessable Content
        invalid request data or invalid referenced type

Business/API errors currently use the standard FastAPI structure:

    {
      "detail": "..."
    }

Pydantic/FastAPI request validation errors retain FastAPI's standard validation
error structure.

A custom global error envelope was intentionally not introduced at this stage.

---

# 8. ID Handling

Node and Edge primary keys are generated by PostgreSQL.

The frontend/client does not create or modify these IDs.

Path parameters use integer IDs:

    /nodes/{node_id}
    /edges/{edge_id}

No additional positive-number validation is imposed on path IDs.

If the requested ID does not correspond to a visible resource, the API returns:

    404 Not Found

The expected future frontend behavior is that users interact with names and
selected graph objects rather than manually entering database IDs.

---

# 9. Multi-Tenant Isolation

Every user-owned Node and Edge operation is scoped by `user_id`.

The API does not trust a `user_id` supplied by the client.

Instead:

    current_user.id

is used internally.

Isolation covers:

- Node creation;
- Node listing;
- Node retrieval;
- Node update;
- Node deletion;
- Edge creation;
- Edge listing;
- Edge retrieval;
- Edge update;
- Edge deletion;
- source Node ownership;
- target Node ownership.

Cross-user Edges are prevented at both API and database levels.

---

# 10. Temporary Authentication

Real authentication is not implemented yet.

The current dependency:

    get_current_user()

uses:

    TEST_USER_ID

to select the current user.

This is intentionally temporary.

The CRUD and multi-tenant architecture is already built around `current_user`,
so a future authentication mechanism can replace how the current user is
resolved without redesigning the ownership rules.
