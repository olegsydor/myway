# My Way — резервне копіювання і тестове відновлення

Docker Compose запускає `postgres:17` як сервіс `db`. Робочі дані зберігаються в томі `postgres_data` за шляхом `/var/lib/postgresql/data`. Скрипт читає лише базу, вказану в `POSTGRES_DB` запущеного контейнера, і записує архів на хості за межами цього тому.

## Створити резервну копію

Потрібні Python 3.10+, Docker Compose і запущений сервіс `db`. Виконуйте з кореня активного My Way у тому самому Docker context і з тією самою конфігурацією Compose, з якою запущено базу. Якщо Compose використовує інший файл або назву проєкту, задайте `COMPOSE_FILE` або `COMPOSE_PROJECT_NAME`. Батьківський каталог для вибраного шляху має існувати.

```sh
python3 scripts/backup_restore.py backup "$HOME/myway-backups"
```

Каталог створюється з правами `0700`. Наявний каталог має належати оператору й бути закритим для інших користувачів. Зберігайте його за межами checkout, на довіреному локальному диску з достатнім місцем і без ACL, що дають іншим доступ. Унікальний каталог успішної копії містить два файли з правами `0600`:

- `database.dump` — повний логічний архів PostgreSQL у custom format.
- `database.dump.sha256` — контрольна сума архіву. Зберігайте обидва файли разом.

Скрипт перевіряє основну версію сервера і утиліт, код завершення `pg_dump`, сигнатуру архіву і повне читання `pg_restore`. Лише після всіх перевірок каталог стає видимим під остаточною назвою. Облікові дані використовуються всередині контейнера. Оператор бачить етап, код помилки й шлях до готового архіву. Вивід PostgreSQL і Docker з потенційно чутливими значеннями прихований.

Архів містить дані користувачів, хеші паролів і службові записи автентифікації. Права доступу захищають файли на локальній файловій системі, а SHA-256 виявляє пошкодження. Архів зберігається у відкритому форматі без шифрування. За потреби використовуйте локальний зашифрований диск. Ролі кластера, налаштування застосунку на кшталт `AUTH_SECRET` та SMTP, і файли поза БД зберігаються окремо від цього архіву.

Якщо команда завершується помилкою, перевірте, чи запущений сервіс `db`, чи він використовує PostgreSQL 17, чи доступний запис до каталогу і чи є місце на диску. Повторіть створення копії. Після примусового переривання може залишитися закритий каталог `.myway-incomplete-*`. Його можна видалити після перевірки, що процес завершився. Зберігайте попередню перевірену копію до успішного завершення нової.

## Перевірити відновлення конкретної копії

Використовуйте архіви з довіреного джерела. Вкажіть каталог, який повернула команда `backup`. Локальний Docker повинен мати образ `postgres:17` (`docker pull postgres:17`, якщо образ відсутній) і достатньо пам’яті для відновленої БД у тимчасовій файловій системі.

```sh
python3 scripts/backup_restore.py restore-test "/повний/шлях/до/myway-…"
```

Скрипт звіряє права та SHA-256, створює новий контейнер PostgreSQL без мережевого доступу, портів і монтування робочих даних, а тоді відновлює архів у нову `myway_restore_test` в одній транзакції. Власники, дозволи та tablespaces вихідного сервера не застосовуються до тестової БД. Після перевірки контейнер автоматично видаляється. У разі аварійного завершення хостового процесу знайдіть залишений контейнер за префіксом `myway-cp5-` і зупиніть тільки контейнер цього запуску.

Успішний `restore-test` підтверджує завантаження конкретного архіву та створення його обмежень у PostgreSQL. Окремий автоматизований сценарій нижче перевіряє роботу застосунку на синтетичній копії.

## Запустити повну перевірку застосунку

```sh
docker build --tag myway-checkpoint5-drill:local .
python3 scripts/backup_restore_drill.py myway-checkpoint5-drill:local
```

Сценарій піднімає чисту ізольовану базу, застосовує Alembic до `head`, створює два тестові акаунти і граф через FastAPI, формує бекап, перевіряє відмову для пошкодженого архіву та відновлює правильний архів в іншому ізольованому PostgreSQL. Окремі контейнери застосунку використовують лише loopback відповідного тестового контейнера. Пошта з підтвердженням реєстрації залишається всередині тимчасового контейнера. Тест порівнює всі публічні таблиці, обмеження, індекси та послідовності, а потім перевіряє здоров’я API, роботу відновленої сесії, вхід з паролем, межі доступу, читання графа та збереження змін у відновленому workspace.

Розклад, зовнішнє сховище та строки зберігання визначаються після вибору хостингу.

Довідка PostgreSQL 17. [pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html) · [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html)
